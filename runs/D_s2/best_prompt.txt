## CRITICAL: the statement MUST compile
A parse or elaboration error scores 0 regardless of faithfulness. Check ALL of the following before answering:

1. **Never use a reserved token or keyword as a binder/variable name.** The most dangerous case is `λ`: it is a reserved token (lambda abstraction), so writing `∀ λ : F, ...` or `(λ : F)` fails with the parse error `unexpected token 'λ'; expected '(', '[', '_', '{' or identifier`. When the natural-language problem uses λ (e.g. an eigenvalue or a scalar parameter), rename it to `μ`, `l`, or `lam`. All other Greek letters (α β γ μ ν ε ι ρ σ τ φ χ ψ ω) are fine as identifiers. Also never use keywords such as `fun`, `let`, `have`, `show`, `match`, `if`, `then`, `else`, `do`, `where`, `in`, `by`, `theorem`, `def`, `Type`, `Sort`, or `Prop` as variable names.

2. **Never write a bare `let x := v` on its own line inside a theorem statement.** In term mode, `let x := v` must either be followed by `;` and the body on the same logical line (`let x := v; body`), or the body must be indented strictly more than the `let` keyword. A `let` whose body sits at the same indentation produces the error "expected '{' or indented tactic sequence" and leaves unsolved metavariable goals (`⊢ ?m._`).
   - Safest option: avoid `let` in the statement entirely — inline the expression where it is used. For example, write
     `MonotoneOn (fun x => f x / x) (Set.Ioi 0)`

Typeclass assumptions go in square brackets, e.g. `[MetricSpace X]`, `[CompleteSpace Y]`, `[Group G]`, `[Field F]`, `[Module F V]`. Implicit binders like `{F V : Type*}` are acceptable when the types are determined by later explicit arguments, but explicit binders are always safe.

4. **Insert coercions explicitly where needed**, e.g. `(-(n : ℤ))` when a natural number is used where an integer is expected.

## General strategy: prefer predicates and quantifiers over heavy machinery
Statements that unfold mathematical objects into quantified predicates over ambient types compile far more reliably than statements built from subtypes, submodules, or specialized structures. For example, "null(T − λI) is invariant under S" is safest stated as `∀ v : V, (T - μ • LinearMap.id) v = 0 → (T - μ • LinearMap.id) (S v) = 0` rather than via `LinearMap.ker` and submodule maps. Similarly, prefer `MonotoneOn`/`ContinuousOn`/`Set.EqOn` over subtypes, and `∃!` with explicit agreement conditions over uniqueness of total functions.
