## Faithfulness rules

## Mathlib facts and compilation pitfalls
- Topological closure is `closure` (lowercase). `Closure` does not exist and raises "unknown identifier".
- Other exact names: `MetricSpace`, `CompleteSpace`, `UniformContinuous`, `Continuous`, `Irreducible`, `Polynomial`, `subset_closure` (of type `s ⊆ closure s`), `Set.inclusion` (of type `s ⊆ t → s → t`).

## Lean 4 syntax pitfalls (observed failures — avoid them)
- Anonymous functions: write `fun x => ...` or `fun x ↦ ...`. NEVER write `λ x, ...` — it gives "unexpected token ','; expected '↦', '=>'".
- `λ` is a reserved token and can never be a variable/binder name ("unexpected token 'λ'; expected '_' or identifier"). For eigenvalues use `μ`, `l`, etc.
- There is no postfix derivative notation `f'`. The derivative of `f : ℝ → ℝ` is the function `deriv f`; at a point, `deriv f x`.
- Limits: `Tendsto g atTop (nhds 0)` expresses "g(x) → 0 as x → +∞" (with `open Topology Filter`).
- **Instance binders `[...]` are ONLY for typeclasses** such as `[Field K]` or `[NormedAddCommGroup V]`. Prop-valued predicates (`Irreducible p`, `IsDomain S`, `Monotone f`, `Continuous f`) are NOT typeclasses: declare them as regular hypotheses `(h : Irreducible p)`, never `[H : Irreducible p]`.
- **No instance binders inside `∃`.** `∃ (a : ℚ) [H : Irreducible f], ...` fails with "unexpected token '['; expected ','". Inside an existential use plain binders and conjunctions: `∃ a, P a ∧ Q a`, or `∃ a (h : P a), Q a`.

## Grading criteria
1. **Compilation**: the statement must compile under the given context with `autoImplicit = false`. Every identifier must be either bound in your theorem or an existing Mathlib name in scope; an unknown identifier is a hard error, never an auto-bound variable. ## Faithfulness rules
- Include EVERY hypothesis from the English text as an explicit named argument. Examples: "a is a nonzero integer" → `(a : ℤ) (ha : a ≠ 0)`; "for n > m" → `(m n : ℕ) (h : m < n)`. Omitting a hypothesis (e.g. forgetting `ha : a ≠ 0`) is a classic faithfulness failure even when the statement compiles.
- Compound descriptions split into several hypotheses: "let p be an odd prime" → `(p : ℕ) (hp : Nat.Prime p) (hodd : Odd p)` — do not drop the oddness.
- Variables introduced with a defining equation ("let 1 + 1/2 + ... + 1/(p-1) = a/b, where a, b are integers") become universally quantified variables plus the equation as a hypothesis: `(a b : ℤ) (h : ... = (a : ℚ) / (b : ℚ))`.
- Reproduce the conclusion exactly, including case splits: "… is 1 or 2 depending on whether a is odd or even" can be encoded as `... = if a % 2 = 0 then 2 else 1`.
- "There exists a unique" → `∃!`.
- Map objects to the right types: integers `ℤ`, naturals `ℕ`, rationals `ℚ`, reals `ℝ`; "ℤ/nℤ" → `ZMod n`; a polynomial over ℚ is `Polynomial ℚ` with indeterminate `X`, e.g. `(X^3 + 6*X + 12 : Polynomial ℚ)`; "irreducible in ℚ" → `Irreducible (p : Polynomial ℚ)`.

## Mathlib facts and compilation pitfalls
- Topological closure is `closure` (lowercase). `Closure` does not exist and raises "unknown identifier".
- Other exact names: `MetricSpace`, `CompleteSpace`, `UniformContinuous`, `Continuous`, `Irreducible`, `Polynomial`, `subset_closure` (of type `s ⊆ closure s`), `Set.inclusion` (of type `s ⊆ t → s → t`), `Nat.Prime`, `Odd`, `IsUnit`, `ZMod`, `Subgroup`, `Subgroup.index`, `Subgroup.relIndex`, `Finset.Icc`, `Finset.range`.
- NEVER invent identifiers. In particular there is NO `IsGroup` in Mathlib — it raises "unknown identifier". If no named predicate exists for a concept, unfold the definition into quantifiers over the available operations. E.g. "ZMod n is not a group under multiplication" means some element has no multiplicative inverse: `∃ a : ZMod n, ∀ b : ZMod n, a * b ≠ 1`.
- NEVER write `...` (ellipsis) in Lean code — it is a syntax error ("unexpected token '...'"). A sum like `1 + 1/2 + ... + 1/(p-1)` must be an explicit finite sum using big operators: `∑ i ∈ Finset.Icc 1 (p - 1), (1 : ℚ) / i` (this needs `open scoped BigOperators`, which the context provides). Match the index set to the endpoints: `Finset.Icc a b` for `a ≤ i ≤ b`, `Finset.range n` for `0 ≤ i < n`.
- Division and casts: with `a b : ℤ`, `a / b` is truncating integer division — rarely the intended meaning for fractions. For rational values, cast: `(a : ℚ) / (b : ℚ)`. Similarly `p ∣ a` with `p : ℕ` and `a : ℤ` needs a cast: `(p : ℤ) ∣ a`. Ensure both sides of each equation/relation live in the same type: a sum of rationals has type `ℚ`, so a right-hand side `a / b` with `a b : ℤ` must be coerced to `ℚ`.
- Subtypes and coercions: if `A : Set X` and `f : A → Y`, then `f` expects an element of the subtype `↥A` (a pair `⟨x, hx⟩`), not a bare `x : X`; writing `f x` with `x : X` is a type mismatch. To express that `g : closure A → Y` extends `f`, write e.g.
  `∀ x : A, g ⟨x.1, subset_closure x.2⟩ = f x`
  or `g ∘ Set.inclusion subset_closure = f`.
- The ambient algebraic structure is not its own substructure: for `(G : Type) [Group G]`, subgroups are `H K : Subgroup G`, and `H ≤ K` typechecks because `Subgroup G` has an `LE` instance. But `K ≤ G` FAILS — `G` is a `Type`, not a `Subgroup G`, and there is no `LE Type` instance ("failed to synthesize instance `LE Type`"). Likewise `H.relIndex G` is a type mismatch because `relIndex` expects a `Subgroup G`. The ambient group viewed as a subgroup is `⊤ : Subgroup G`. A hypothesis "K ≤ G" is already fully encoded by `K : Subgroup G` — do not write it as a `≤` statement.
- Subgroup indices: `[G : H]` is `H.index` (i.e. `Subgroup.index H : ℕ`); the relative index `[K : H]` for `H ≤ K` is `H.relIndex K`. When the context defines a helper (e.g. `noncomputable def Subgroup.relindex {G : Type*} [Group G] (H K : Subgroup G) : ℕ := H.relIndex K`), use that helper name in your statement: "|G:H| = |G:K|·|K:H|" → `H.index = K.index * Subgroup.relindex H K`.
- `gcd` on `ℤ` (Mathlib's `GCDMonoid ℤ` instance) returns a non-negative `ℤ`, so it can be compared directly with the literals `1` and `2`.
- Annotate types where literals are ambiguous, e.g. `(... : Polynomial ℚ)`; write multiplication explicitly as in `6*X`.
- `MetricSpace X`, `CompleteSpace Y`, `Group G` etc. are typeclasses — supply them as instance arguments `[MetricSpace X]`, `[Group G]`.

## Faithfulness requirement (critical — checked by a judge after compilation)
Compiling is necessary but NOT sufficient. A judge then compares your statement to the original problem. Observed unfaithfulness failures to avoid:
- **Do not drop hypotheses.** Every hypothesis in the problem must appear. E.g. "H is a subgroup of (ℚ,+) with the property that 1/x ∈ H for every nonzero x ∈ H" REQUIRES the hypothesis `(hH : ∀ x ∈ H, x ≠ 0 → (1 / x) ∈ H)` — stating only the conclusion `H = ⊥ ∨ H = ⊤` is unfaithful.
- **Count the hypotheses one by one.** "f(x), f′(x), f′′(x), f′′′(x) are positive for all x" is FOUR separate hypotheses (one per derivative order). "f has a continuous third derivative" is also a hypothesis — do not silently replace it with bare differentiability of f and drop the continuity of f′′′.
- **Do not arbitrarily restrict domains.** "f is continuous for x ≥ 0" is `ContinuousOn f (Set.Ici 0)`, NOT `ContinuousOn f (Set.Ico 0 1)`.
- **Do not widen conclusions beyond the problem's domain.** If the object is only defined/considered on a subdomain (e.g. `g(x) = f(x)/x` only for `x > 0`), the conclusion must be scoped: `MonotoneOn (fun x => f x / x) (Set.Ioi 0)`, NOT the global `Monotone (fun x => f x / x)`.
- **Match the quantifier structure exactly.** "There are infinitely many a such that P a" is `Set.Infinite {a | P a}` — NOT `∃ a, ∀ a', a = a'`. "For all ... exists ..." must keep its order.
- **Use the specific objects given.** If the problem names a concrete polynomial/function/ring element (e.g. `x^7 + 15x^2 - 30x + a`, or the elements `2, √-n, 1+√-n`), write it out explicitly; do not replace it with an arbitrary variable.

## Lean 4 syntax pitfalls (observed failures — avoid them)
- Anonymous functions: write `fun x => ...` or `fun x ↦ ...`. NEVER write `λ x, ...` — it gives "unexpected token ','; expected '↦', '=>'".
- `λ` is a reserved token and can never be a variable/binder name. For eigenvalues use `μ`, `l`, etc.
- There is no postfix derivative notation `f'`. The derivative of `f : ℝ → ℝ` is the function `deriv f`; at a point, `deriv f x`.
- Limits: `Tendsto g atTop (nhds 0)` expresses "g(x) → 0 as x → +∞" (with `open Topology Filter`).
- **Instance binders `[...]` are ONLY for typeclasses** such as `[Field K]` or `[NormedAddCommGroup V]`. Prop-valued predicates (`Irreducible p`, `IsDomain S`, `Monotone f`, `Continuous f`, `ContDiff ℝ 3 f`) are NOT typeclasses: declare them as regular hypotheses `(h : Irreducible p)`, never `[H : Irreducible p]`.
- **No instance binders inside `∃`.** `∃ (a : ℚ) [H : Irreducible f], ...` fails with "unexpected token '['; expected ','". Inside an existential use plain binders and conjunctions: `∃ a, P a ∧ Q a`, or `∃ a (h : P a), Q a`.
- **Only use notation that actually exists in Mathlib.** Invented notation fails at PARSE time. E.g. `ℤ[√-n]` gives "unexpected token at this precedence level; consider parenthesizing the term": the bracket notation `R[X]` is reserved for polynomials (`Polynomial R`) and there is no "adjoin an element" bracket notation for types. (Also, `√` is `Real.sqrt` notation, so `√-n` would be a real number, not a ring to ascribe elements to.) See "Concrete rings" below for the correct tool.

## Typeclass pitfalls (observed failures — avoid them)
- Structures are typeclasses on a carrier type, not types. Write `(K : Type) [Field K]`, `(V : Type*) [NormedAddCommGroup V] [InnerProductSpace ℂ V] [FiniteDimensional ℂ V]`. NEVER write `(V : InnerProductSpace ℂ)`.
- The conclusion must be a `Prop`. Classes like `IntegralDomain R`, `Field K`, `Group G` are NOT Props and cannot be the conclusion. Use Prop-valued predicates: `IsDomain S`, `IsSelfAdjoint T`, `Module.End.HasEigenvalue T μ`, `Irreducible p`, `Tendsto ...`, etc.
- Instance synthesis must succeed. E.g. using `IntegralDomain R` with only `[Ring R]` declared fails with "failed to synthesize instance ... CommSemiring R". Either declare all needed instances explicitly or, better, use bundled subtypes that carry instances automatically.

## Global vs `...On` predicates: the set argument must be a `Set` (observed failure)
- `ContinuousOn f s`, `MonotoneOn f s`, `StrictMonoOn f s`, `DifferentiableOn ℝ f s` take `s : Set ℝ`. Passing the TYPE `ℝ` is a type error: `ContinuousOn f ℝ` → "Application type mismatch: The argument ℝ has type Type ... but is expected to have type Set ℝ".
- When the property holds on the whole domain ("for all x"), use the GLOBAL predicate instead: `Continuous f`, `Monotone f`, `∀ x, DifferentiableAt ℝ f x`. (`ContinuousOn f Set.univ` would also compile, but the global form is cleaner and more idiomatic.)
- Domain sets: "x ≥ a" → `Set.Ici a`; "x > a" → `Set.Ioi a`; "x ≤ a" → `Set.Iic a`; "x < a" → `Set.Iio a`; "a ≤ x ≤ b" → `Set.Icc a b`; "a ≤ x < b" → `Set.Ico a b`.
- "f differentiable for all x > 0": `∀ x > 0, DifferentiableAt ℝ f x` (expands to `∀ x, x > 0 → ...`; fine).
- "f' is monotonically increasing for x > 0": `MonotoneOn (deriv f) (Set.Ioi 0)`.

## Derivatives: first, higher-order, and "continuous n-th derivative"
- First derivative: `deriv f` (as a function), `deriv f x` (at a point).
- Higher derivatives iterate: `deriv (deriv f)`, `deriv (deriv (deriv f))` (equivalently `iteratedDeriv 2 f`, `iteratedDeriv 3 f`).
- "f has a continuous third derivative" / "f is C³": the idiomatic single hypothesis is `(hf : ContDiff ℝ 3 f)`. It implies all lower-order differentiability and the continuity of f′′′, so you do not need separate `DifferentiableAt` hypotheses. (If you hand-list hypotheses instead, you need `DifferentiableAt` at each level PLUS `Continuous (deriv (deriv (deriv f)))`.)
- Positivity of each derivative is a SEPARATE hypothesis, e.g.: `(h0 : ∀ x, 0 < f x) (h1 : ∀ x, 0 < deriv f x) (h2 : ∀ x, 0 < deriv (deriv f) x) (h3 : ∀ x, 0 < deriv (deriv (deriv f)) x)`.

## Concrete rings: `Zsqrtd`, `GaussianInt` (observed failure)
- The ring ℤ[√d] (for `d : ℤ`) is the bundled type `Zsqrtd d`; it is a `CommRing` for every `d : ℤ`, so `Irreducible`, `+`, `*`, numerals, and `1` all work directly.
- `Zsqrtd.sqrtd : Zsqrtd d` denotes √d; `⟨a, b⟩` denotes a + b√d.
- With `n : ℕ`, coerce before negating: `Zsqrtd (-(n : ℤ)))` (equivalently `Zsqrtd (-↑n)`).
- Example — "2, √-n and 1+√-n are irreducible in ℤ[√-n]": `Irreducible (2 : Zsqrtd (-(n : ℤ))) ∧ Irreducible (Zsqrtd.sqrtd : Zsqrtd (-(n : ℤ))) ∧ Irreducible (1 + Zsqrtd.sqrtd : Zsqrtd (-(n : ℤ)))`.
- The Gaussian integers ℤ[i] are `GaussianInt` (notation `ℤ[i]` exists; it is `Zsqrtd (-1)`). But there is NO analogous `ℤ[√-n]` notation — use `Zsqrtd`.
- Squarefree hypotheses: `Nat.SquareFree n` for `n : ℕ`; `Squarefree a` for a general monoid (e.g. ℤ).

## "Not an integer", "positive integer", and similar rephrasings (observed success — reuse these patterns)
- "√m is not an integer" (for `m : ℤ` or `ℕ`): rephrase inside ℤ as `¬ ∃ k : ℤ, k ^ 2 = m`. There is no convenient `IsInteger` predicate for reals, and routing through `Real.sqrt` is unnecessary — an integer is a perfect square iff its real square root is an integer, so this is faithful.
- "There exists a positive integer n such that P n": `∃ (n : ℕ) (hn : n > 0), P n` or `∃ n : ℕ, 0 < n ∧ P n`.
- Mixed ℕ/ℤ arithmetic coerces automatically: with `n : ℕ` and `a b c : ℤ`, the expression `n ^ 3 + a * n ^ 2 + b * n + c` elaborates in ℤ (Lean inserts `↑n`).

## Bundled subobjects: use `⊥` and `⊤`, never coerced `0` or the whole type (observed failures)
For `H : AddSubgroup G` / `Subgroup G` / `Subring R` / `Ideal R` / `Submodule R M`:
- The trivial (smallest) subobject is `⊥`; the whole (largest) one is `⊤`. "H = 0 or H = ℚ" becomes `H = ⊥ ∨ H = ⊤`.
- NEVER write `H = (0 : G)` — error: "Type mismatch: 0 has type G but is expected to have type AddSubgroup G".
- NEVER write `H = (G : AddSubgroup G)` — error: "Type mismatch: G has type Type ... but is expected to have type AddSubgroup G".
- Membership works directly: `x ∈ H`, and bounded quantifiers `∀ x ∈ H, P x` are fine.
- Coerce to a set with `(H : Set G)` if needed.
- For a group written additively (e.g. ℚ under +), use `AddSubgroup`, not `Subgroup`.

## "Infinitely many"
- "There are infinitely many a : ℤ such that P a": `Set.Infinite {a : ℤ | P a}` (equivalently `¬ {a : ℤ | P a}.Finite`). The set-builder form is standard and always available under `import Mathlib`.

## Polynomials
- With `open Polynomial`, build polynomials from `X` (indeterminate) and `C` (constant embedding `R → R[X]`); `R[X]` is notation for `Polynomial R` — and ONLY for polynomials.
- Example: `X ^ 7 + C 15 * X ^ 2 - C 30 * X + C a`. Numerals like `15` elaborate in any ring via `OfNat`.
- To use an integer coefficient `a : ℤ` in a polynomial over ℚ, coerce: `C (a : ℚ)`.
- If the coefficient ring is ambiguous, ascribe the whole expression: `(X ^ 7 + C 15 * X ^ 2 - C 30 * X + C (a : ℚ) : ℚ[X])`.
- Irreducibility is the Prop predicate `Irreducible p` (a hypothesis `(h : Irreducible p)`, never an instance).

## Mathlib names/patterns that exist and typecheck
- Subring of a field: `(S : Subring K)` with `(K : Type) [Field K]`. A `Subring` contains `1` by definition and inherits `CommRing` from `K`; state the conclusion as `IsDomain S`. Do NOT invent classes like `IsSubring R K` or `OneClass R`.
- Linear operator on a complex inner-product space: `(T : V →ₗ[ℂ] V)` with `(V : Type*) [NormedAddCommGroup V] [InnerProductSpace ℂ V] [FiniteDimensional ℂ V]`.
- Adjoint: `LinearMap.adjoint T` (dot notation `T.adjoint`). Self-adjoint: `IsSelfAdjoint T`. Normal: `IsStarNormal T`, or explicitly `T.adjoint * T = T * T.adjoint`.
- "μ is an eigenvalue of T": `Module.End.HasEigenvalue T μ`.
- "μ is real" for `μ : ℂ`: `μ.im = 0` or `(μ.re : ℂ) = μ`. Note `μ.re : ℝ`, so `μ.re = μ` does NOT typecheck without a coercion.
- Smoothness: `ContDiff ℝ n f` ("f is Cⁿ"); `iteratedDeriv n f` (n-th derivative).
- Quadratic integer rings: `Zsqrtd d`, `Zsqrtd.sqrtd`, `GaussianInt` (`ℤ[i]`); `Nat.SquareFree n`, `Squarefree a`.

## General strategy
1. Parse the problem into objects, hypotheses, and conclusion. List EVERY hypothesis explicitly as a numbered list — each one must appear in your statement, and your binder list should have the same count (e.g. four positivity hypotheses for f, f′, f′′, f′′′).
2. Map each object to a standard Mathlib type, preferring bundled types (`Subring K`, `Subgroup G`, `AddSubgroup G`, `Ideal R`, `Module.End ℂ V`, `Zsqrtd d`, `GaussianInt`) over ad-hoc predicates or invented notation, since they bring the required instances. For bundled subobjects use `⊥`/`⊤` for trivial/whole, and `x ∈ H` for membership.
3. Declare typeclasses as instance arguments `[...]` and Prop hypotheses as regular arguments `(...)`. Never mix these up.
4. Identify the exact domain of every quantifier and every property (`x ≥ 0` vs `x > 0` vs all `x`; integers vs rationals). If the domain is a proper subset, choose `Set.Ici`/`Set.Ioi`/etc. together with `ContinuousOn`/`MonotoneOn`/`DifferentiableOn`; if it is the whole type, use the GLOBAL predicates (`Continuous f`, `Monotone f`, `∀ x, DifferentiableAt ℝ f x`) — never pass the type `ℝ` where a `Set ℝ` is expected. Scope hypotheses AND the conclusion to exactly the domains in the problem — no more, no less.
5. State the conclusion with existing Mathlib Prop predicates, faithfully matching the problem's logical structure: "infinitely many" → `Set.Infinite {x | P x}`; "for all" / "there exists" in the right order; concrete given objects written out explicitly.
6. Rephrase notions with no direct Mathlib predicate into elementary equivalent ones: "√m is not an integer" → `¬ ∃ k : ℤ, k ^ 2 = m`; "C³ function" → `ContDiff ℝ 3 f`.
7. Before using any non-basic notation or identifier, ask whether you have actually seen it in Mathlib. Parse errors like "unexpected token at this precedence level; consider parenthesizing the term" mean you invented notation (e.g. `ℤ[√-n]`); "Application type mismatch ... expected type Set ℝ" means you passed a type where a set was expected. If unsure whether a fancy name exists, rephrase using more basic, certainly-existing concepts.
8. Mentally compile before answering: valid Lean 4 syntax (no `λ` binders, no `λ x,` lambdas, no `[...]` around Props, no `[...]` inside `∃`), all identifiers exist in Mathlib, every typeclass mentioned is derivable from your declared instances, and every term has the right type (an `AddSubgroup`/`Subgroup` is neither a `Type` nor an element of the group; a `Set ℝ` is not the type `ℝ`).

## Set unions and intersections: pick the right operator (observed parse errors)
- **Binary:** `A ∪ B`, `A ∩ B` — infix, exactly two sets. NEVER with a binder: `(∩ i, C i)` fails with "unexpected token '∩'; expected ')', '_', '↑', '↥', '⇑', identifier or term".

## Lean 4 syntax pitfalls (observed failures — avoid them)
- Anonymous functions: write `fun x => ...` or `fun x ↦ ...`. NEVER write `λ x, ...` — it gives "unexpected token ','; expected '↦', '=>'".
- `λ` is a reserved token and can never be a variable/binder name. For eigenvalues use `μ`, `l`, etc.
- There is no postfix derivative notation `f'`. The derivative of `f : ℝ → ℝ` is the function `deriv f`; at a point, `deriv f x`.
- Limits: `Tendsto g atTop (nhds 0)` expresses "g(x) → 0 as x → +∞" (with `open Topology Filter`).
- **Instance binders `[...]` are ONLY for typeclasses** such as `[Field K]` or `[NormedAddCommGroup V]`. Prop-valued predicates (`Irreducible p`, `IsDomain S`, `Monotone f`, `Continuous f`, `ContDiff ℝ 3 f`, `IsClosed s`, `IsOpen s`) are NOT typeclasses: declare them as regular hypotheses `(h : Irreducible p)`, never `[H : Irreducible p]`.
- **No instance binders inside `∃`.** `∃ (a : ℚ) [H : Irreducible f], ...` fails with "unexpected token '['; expected ','". Inside an existential use plain binders and conjunctions: `∃ a, P a ∧ Q a`, or `∃ a (h : P a), Q a`. (Plain hypothesis binders inside `∃`, like `∃ t : Set (Set ℝ), t.Countable ∧ P t`, are fine.)
- **Only use notation that actually exists in Mathlib.** Invented notation fails at PARSE time. E.g. `ℤ[√-n]` gives "unexpected token at this precedence level; consider parenthesizing the term": the bracket notation `R[X]` is reserved for polynomials (`Polynomial R`) and there is no "adjoin an element" bracket notation for types. (Also, `√` is `Real.sqrt` notation, so `√-n` would be a real number, not a ring to ascribe elements to.) See "Concrete rings" below for the correct tool.

## Typeclass pitfalls (observed failures — avoid them)
- Structures are typeclasses on a carrier type, not types. Write `(K : Type) [Field K]`, `(V : Type*) [NormedAddCommGroup V] [InnerProductSpace ℂ V] [FiniteDimensional ℂ V]`, `(X : Type*) [TopologicalSpace X]`. NEVER write `(V : InnerProductSpace ℂ)` or `(X : TopologicalSpace)`.
- The conclusion must be a `Prop`. Classes like `IntegralDomain R`, `Field K`, `Group G`, `MetricSpace X` are NOT Props and cannot be the conclusion. Use Prop-valued predicates: `IsDomain S`, `IsSelfAdjoint T`, `Module.End.HasEigenvalue T μ`, `Irreducible p`, `Tendsto ...`, `MetrizableSpace X`, etc.
- Instance synthesis must succeed. E.g. using `IntegralDomain R` with only `[Ring R]` declared fails with "failed to synthesize instance ... CommSemiring R". Either declare all needed instances explicitly or, better, use bundled subtypes that carry instances automatically.

## Global vs `...On` predicates: the set argument must be a `Set` (observed failure)

- When the property holds on the whole domain ("for all x"), use the GLOBAL predicate instead: `Continuous f`, `Monotone f`, `∀ x, DifferentiableAt ℝ f x`. (`ContinuousOn f Set.univ` would also compile, but the global form is cleaner and more idiomatic.)
- Domain sets: "x ≥ a" → `Set.Ici a`; "x > a" → `Set.Ioi a`; "x ≤ a" → `Set.Iic a`; "x < a" → `Set.Iio a`; "a ≤ x ≤ b" → `Set.Icc a b`; "a ≤ x < b" → `Set.Ico a b`; "a < x < b" → `Set.Ioo a b`.

## Derivatives: first, higher-order, and "continuous n-th derivative"
- First derivative: `deriv f` (as a function), `deriv f x` (at a point).
- Higher derivatives iterate: `deriv (deriv f)`, `deriv (deriv (deriv f))` (equivalently `iteratedDeriv 2 f`, `iteratedDeriv 3 f`).
- "f has a continuous third derivative" / "f is C³": the idiomatic single hypothesis is `(hf : ContDiff ℝ 3 f)`. It implies all lower-order differentiability and the continuity of f′′′, so you do not need separate `DifferentiableAt` hypotheses. (If you hand-list hypotheses instead, you need `DifferentiableAt` at each level PLUS `Continuous (deriv (deriv (deriv f)))`.)
- Positivity of each derivative is a SEPARATE hypothesis, e.g.: `(h0 : ∀ x, 0 < f x) (h1 : ∀ x, 0 < deriv f x) (h2 : ∀ x, 0 < deriv (deriv f) x) (h3 : ∀ x, 0 < deriv (deriv (deriv f)) x)`.

## General strategy
1. Parse the problem into objects, hypotheses, and conclusion. List EVERY hypothesis explicitly as a numbered list — each one must appear in your statement, and your binder list should have the same count (e.g. four positivity hypotheses for f, f′, f′′, f′′′). ALSO list every conjunct of the conclusion (e.g. "countable collection of disjoint segments whose union is s" = countable ∧ all segments ∧ pairwise disjoint ∧ union equals s) — each must appear.
2. Check the context for custom `def`s. If the context defines the central notion (e.g. `countably_compact`), state the theorem about THAT definition with its exact name; do not substitute or add a similarly named Mathlib class, and do not add any hypothesis or instance the problem does not state.
3. Map each object to a standard Mathlib type, preferring bundled types (`Subring K`, `Subgroup G`, `AddSubgroup G`, `Ideal R`, `Module.End ℂ V`, `Zsqrtd d`, `GaussianInt`) over ad-hoc predicates or invented notation, since they bring the required instances. For bundled subobjects use `⊥`/`⊤` for trivial/whole, and `x ∈ H` for membership. For topological spaces use `(X : Type*) [TopologicalSpace X]`; for subspaces use `s : Set X` plus `(h : IsClosed s)` — the subtype `↥s` gets the topology automatically.
4. Declare typeclasses as instance arguments `[...]` and Prop hypotheses as regular arguments `(...)`. Never mix these up. Remember `MetricSpace` is a class (not a Prop): "metrizable" is `MetrizableSpace`; "Hausdorff" is `T2Space`.
5. Identify the exact domain of every quantifier and every property (`x ≥ 0` vs `x > 0` vs all `x`; integers vs rationals). If the domain is a proper subset, choose `Set.Ici`/`Set.Ioi`/etc. together with `ContinuousOn`/`MonotoneOn`/`DifferentiableOn`; if it is the whole type, use the GLOBAL predicates (`Continuous f`, `Monotone f`, `∀ x, DifferentiableAt ℝ f x`) — never pass the type `ℝ` where a `Set ℝ` is expected. Scope hypotheses AND the conclusion to exactly the domains in the problem — no more, no less.
6. State the conclusion with existing Mathlib Prop predicates, faithfully matching the problem's logical structure: "infinitely many" → `Set.Infinite {x | P x}`; "for all" / "there exists" in the right order; concrete given objects written out explicitly.
7. For every union/intersection, choose the operator by shape: two sets → `∪`/`∩`; indexed family → `⋃ i, ...` / `⋂ i, ...` (binder + comma mandatory); a set of sets → `⋃₀ t` / `⋂₀ t`.
8. Rephrase notions with no direct Mathlib predicate into elementary equivalent ones: "√m is not an integer" → `¬ ∃ k : ℤ, k ^ 2 = m`; "C³ function" → `ContDiff ℝ 3 f`; "at most countable" → `t.Countable`; "pairwise disjoint" → `t.PairwiseDisjoint id`; "each piece is a segment" → `∀ u ∈ t, ∃ a b : ℝ, u = Set.Ioo a b`.
9. Before using any non-basic notation or identifier, ask whether you have actually seen it in Mathlib. Parse errors like "unexpected token at this precedence level; consider parenthesizing the term" mean you invented notation (e.g. `ℤ[√-n]`); "unexpected token '∧'; expected ','" after a big operator means the binder is missing (use `⋃₀`/`⋂₀` for a set of sets); "unexpected token '∩'" means you used a binary operator with a binder (use `⋂`); "type expected, got (TopologicalSpace ...)" means you used a typeclass as a type; "Application type mismatch ... expected type Set ℝ" means you passed a type where a set was expected. If unsure whether a fancy name exists, rephrase using more basic, certainly-existing concepts.
10. Mentally compile before answering: valid Lean 4 syntax (no `λ` binders, no `λ x,` lambdas, no `[...]` around Props, no `[...]` inside `∃`), all identifiers exist in Mathlib, every typeclass mentioned is derivable from your declared instances, and every term has the right type (an `AddSubgroup`/`Subgroup` is neither a `Type` nor an element of the group; a `Set ℝ` is not the type `ℝ`; `TopologicalSpace X` is an instance on the carrier `X : Type*`, not itself a carrier).
